В этих задачах нужно рецензировать предложенный проект до выпуска. В отличие от [задач на рассуждение](scenarios.md), здесь исходная точка — конкретный артефакт: схема данных, контракт API или конфигурация. Для каждого проекта выпишите нарушенный инвариант, покажите отказное окно, предложите изменённый артефакт и назовите цену решения. Название паттерна без работающего протокола не считается исправлением.

Все числа, сервисы и требования учебные. Конфигурации и блоки `text` описывают проектный контракт, а не готовые настройки конкретного продукта. SQL показывает существенную часть решения; обработка ошибок и проверки доступа подразумеваются только там, где они явно оговорены. Перед раскрытием разбора отведите на ревью 15–20 минут.

## Надёжная запись и согласованное чтение

### 1. Надёжная доставка существует только между commit и publish

Сервис договоров обещает: каждый подтверждённый договор когда-нибудь попадёт в поисковый индекс; неподтверждённый не появится. Поиск может отставать на минуту. При недоступности брокера API должен продолжать сохранять договоры. На ревью принесли такой поток:

```text
BEGIN database transaction
INSERT contract(id, revision, body)
COMMIT
publish ContractCreated(id, body) to broker
if publish failed: write error to application log
return 201
consumer: upsert search document by contract_id
```

Найдите оба вида рассогласования при перестановке `publish` и `COMMIT`. Исправьте не только отправку, но и применение повторных и переставленных событий.

<details>
<summary>Разбор</summary>

После commit процесс может завершиться до отправки, поэтому журнал ошибок даже не появится. Обратный порядок допускает публикацию договора, транзакция которого затем откатится. Надёжность брокера начинает действовать после принятия сообщения и не закрывает это окно приложения. Подтверждение клиенту должно означать, что сохранены договор и устойчивое обязательство доставить изменение.

Исправленный артефакт связывает их локальной транзакцией:

```text
TX: INSERT contract(id, revision=1, body)
    INSERT outbox(event_id, contract_id, revision=1, body)
COMMIT; return 201
relay: read unsent outbox -> publish -> await broker acknowledgement
relay: mark event delivered only after acknowledgement
consumer: atomically replace document only if incoming_revision > stored_revision
equal revision + equal event: successful no-op; conflicting payload: alert
```

У outbox нужен уникальный `event_id`; у договора — монотонная ревизия. Если relay упал после принятия сообщения брокером, но до отметки, он отправит дубль. Это штатное отказное окно, поэтому обещать единственную доставку нельзя. Поисковый адаптер должен атомарно проверять ревизию в той системе, где меняется документ; отдельная проверка в памяти перед безусловным upsert оставит гонку. Для удалений передают ревизию tombstone, иначе старый `Created` воскресит документ.

Проверка останавливает процесс после каждого шага, переставляет ревизии 2 и 3, повторяет удаление и восстанавливает relay после двух часов простоя. Сверяют версии договора и индекса, возраст старейшей недоставленной записи и запас места outbox. Пока брокер недоступен, минутная свежесть поиска не выполнима: API может сохранять договоры, но состояние поиска должно показывать деградацию.

Цена — дополнительная запись на каждое изменение, место до доставки, эксплуатация relay и механизм сверки. Удаление outbox по одному возрасту без подтверждения доставки снова нарушит инвариант.

</details>

### 2. Кэш дедупликации заменил бизнес-ограничение

Партнёр загружает строки счетов и может переотправлять один файл семь суток. Одна строка с ключом `(partner_id, invoice_id, line_no)` должна начислить комиссию ровно один раз за всё время хранения финансового журнала. Исправленный файл с тем же ключом и другой суммой должен давать конфликт, а не новое начисление.

```text
key = partner_id + invoice_id + line_no
if Redis.GET(key): return 200
INSERT commission_ledger(random_id, amount)
Redis.SET(key, "done", TTL=600 seconds)
return 200
Redis unavailable -> bypass deduplication
nightly: clear Redis to reclaim memory
```

Какие проблемы не исправит TTL в восемь суток? Покажите новое место обеспечения уникальности и поведение после потери ответа.

<details>
<summary>Разбор</summary>

Десятиминутный TTL покрывает только короткую часть семисуточного окна повторов. Однако увеличение TTL не исправляет одновременные запросы, падение между БД и Redis, очистку кэша и режим обхода при отказе. В исходной таблице нет бизнес-ключа, поэтому даже последующая сверка не сможет надёжно отличить дубль от отдельного начисления.

Бизнес-ограничение переносится в устойчивый журнал, а Redis остаётся ускорителем:

```sql
CREATE UNIQUE INDEX commission_business_key
  ON commission_ledger(partner_id, invoice_id, line_no);
-- В одной транзакции:
INSERT INTO commission_ledger
  (partner_id, invoice_id, line_no, amount, payload_hash)
VALUES (:partner, :invoice, :line, :amount, :hash)
ON CONFLICT (partner_id, invoice_id, line_no) DO NOTHING;
-- При конфликте прочитать сохранённую строку и сравнить payload_hash.
```

Сервер возвращает прежний результат при совпадении значимых параметров, а при другом содержимом — документированный конфликт. Хэш вычисляют по каноническому бизнес-представлению: различие пробелов JSON не должно создавать разные операции. Если начисление меняет ещё и итоговый баланс, вставка и изменение баланса входят в одну транзакцию; баланс меняют только при действительно вставленной строке. Простого уникального индекса после отдельного изменения баланса недостаточно.

Потеря ответа после commit безопасна: повтор находит прежнюю операцию. Потеря Redis тоже безопасна, но увеличивает поток к БД. При 300 строках/с семисуточный кэш содержит до `300 × 604800 = 181440000` ключей; даже условные 100 байт на ключ дают 18,144 ГБ без реплик и дополнительных расходов. Это полезный расчёт стоимости, но не причина удалять бизнес-историю.

Проверяют два параллельных запроса, изменённую сумму, полный сброс Redis и падение перед ответом. Компоненты бизнес-ключа обязательны и не допускают NULL. Цена — индекс и хранение ключей вместе с журналом. Для архивирования нужен отдельный контракт: если записи удаляются, прежние ключи должны оставаться запрещёнными либо API обязан отклонять старый период, а не снова начислять комиссию.

</details>

### 3. Реплика выбрана раньше проверки свежести

После изменения счёта API возвращает его ревизию. Следующий GET с этой ревизией обязан показать счёт и строки не старее подтверждённого изменения; допускается временная ошибка при недостижимой свежести. Все изменения строк повышают ревизию родительского счёта в той же транзакции.

```text
PUT /invoices/42 -> primary commit revision=19 -> 200
GET /invoices/42?min_revision=19 -> random replica
SELECT revision FROM invoices WHERE id=42
if revision < 19: sleep 100ms
SELECT header FROM invoices WHERE id=42
SELECT lines FROM invoice_lines WHERE invoice_id=42
return 200 even if replica is still behind
```

Найдите дефекты ожидания и составного чтения. Как должен выглядеть контракт маршрутизации при лаге 15 секунд и deadline GET 500 мс?

<details>
<summary>Разбор</summary>

Пауза 100 мс ничего не доказывает о продвижении реплики. Более того, проверка ревизии и последующие запросы не объединены снимком: можно собрать заголовок и строки разных состояний. Минимальная ревизия относится к конкретному счёту, поэтому её нельзя сравнивать с произвольным общим счётчиком другого шарда.

Исправленный проект явно ограничивает ожидание и проверяет весь ответ:

```text
token = signed(tenant_id, invoice_id, min_revision=19)
read candidate replica in one consistent read-only snapshot
load header + lines; require header.revision >= token.min_revision
if behind: rollback snapshot, wait within 150ms budget, retry with NEW snapshot
if still behind: read same aggregate from primary within remaining deadline
if no qualifying result before 500ms: return freshness_unavailable
never label an older response as satisfying min_revision
```

Новое чтение после ожидания важно: в сохраняемом снимке более свежие изменения сами не появятся. В PostgreSQL для нескольких запросов подойдёт согласованный снимок `REPEATABLE READ`; один SQL, собирающий весь агрегат, также избегает смешивания разных снимков операторов.

Если реплика уже содержит ревизию 20, она удовлетворяет минимуму 19. Это не требование вернуть именно историческую версию. Подпись токена не заменяет проверку tenant и прав пользователя. Клиент без токена получает отдельно оговорённую eventual consistency; межустройственная гарантия требует передачи минимума через общий контекст, а не автоматически возникает из ответа PUT.

Проверка удерживает реплику на 18, меняет строки во время GET и отключает primary. Ни в одном случае нельзя вернуть старое состояние как свежее. Отдельно проверяют failover: проект предполагает сохранность подтверждённой ревизии на допустимом новом primary; асинхронная репликация сама этого не обещает. Цена — дополнительные чтения, доля запросов к primary и временные отказы при сетевом разделении.

</details>

### 4. Инвалидация удаляет ключ, но не право его наполнить

Сервис собирает тяжёлое дерево прав отображения интерфейса. После успешного изменения следующий начавшийся GET обязан использовать новую ревизию дерева. Результат сборки занимает секунду, его кэшируют на час. Изменения и номер ревизии хранятся в одной БД; разрешён дополнительный дешёвый запрос ревизии на primary.

```text
GET: miss cache[tenant] -> read old tree -> build for 1 second
PUT: update tree in database; COMMIT
PUT: DELETE cache[tenant]; return 200
GET: SET cache[tenant] = old built tree, TTL=1 hour
next GET: return cache[tenant] without consulting database
if invalidation fails: log and continue
background: delete the same key again after 2 seconds
```

Исправьте гонку без предположения о максимальной длительности остановки читателя. Что именно будет стоить строгая гарантия?

<details>
<summary>Разбор</summary>

Удаление не отменяет уже запущенную сборку. Второе удаление через две секунды тоже не является доказательством: процесс может возобновиться через минуту. Поскольку условие допускает чтение актуальной ревизии на primary, можно убрать инвалидацию из критического протокола корректности и адресовать неизменяемые результаты по ревизии.

```text
PUT TX: change all tree rows; increment tenant.tree_revision; COMMIT
GET: read current revision r from authoritative primary
GET: lookup cache[(tenant_id, r, renderer_version)]
on miss: start consistent snapshot on primary; read revision s and all tree rows
require s == r; otherwise restart with s
build immutable result; SETNX cache[(tenant_id, r, renderer_version)]
return tree of revision r; TTL only reclaims obsolete versions
```

Чтение ревизии и строк внутри сборки должно видеть один снимок. Нельзя взять новую ревизию и построить под её ключом старые строки с отставшей реплики. Читатель, начавшийся до commit, вправе завершить ответ старой ревизией по сформулированному условию. Любой начавшийся после подтверждения PUT сначала читает primary и выбирает новый ключ. Старый сборщик может заполнить старый ключ, но следующий запрос на него уже не попадёт.

При недоступности primary строгий GET отказывает. Если продукт хочет продолжать работу со старым деревом, это отдельный режим с другой гарантией, который нельзя молча объявить эквивалентным. Само дерево интерфейса также не должно быть единственным механизмом разрешения серверных операций.

Проверка приостанавливает сборку ревизии 7, завершает изменение до 8, возобновляет сборщик и запускает новый GET. Дополнительно моделируют вытеснение кэша и смену формата renderer: смешение форматов предотвращает часть ключа `renderer_version`.

Цена — обязательный небольшой запрос к primary на каждый GET и хранение нескольких версий дерева. Сборку объединяют по полному ключу, ограничивают конкурентность и TTL старых версий. Кэширование самой «актуальной ревизии» на час восстановит исходную проблему и нарушит требование свежести.

</details>

## Распределение работы и границы владения

### 5. Большой tenant не помещается в единицу шардирования

Хранилище документов имеет 24 физических шарда. Каждый выдерживает 3000 записей/с, рабочий предел с запасом — 2100. Один tenant создаёт 24000 записей/с в разные документы; порядок нужен только внутри документа. Другие tenants дают примерно 500 записей/с на каждый шард.

```text
shard = hash(tenant_id) % 24
document primary key = (tenant_id, document_id)
all commands for tenant go to its shard
on overload: add 24 more shards
move tenant: copy rows, then change hash modulo
during copy: both shards accept writes
deduplication keys stored only on current shard
```

Почему добавление машин не доказывает выполнимость? Предложите конкретную единицу маршрутизации и безопасную смену владельца.

<details>
<summary>Разбор</summary>

Ключ маршрутизации делает tenant неделимым. Его 24000 записей/с превышают даже физический предел одного шарда в восемь раз. Дополнительные машины меняют место горячей точки, а не её размер. Смена модуля ещё и перемещает множество других tenants, создавая массовый backfill одновременно с перегрузкой.

Для независимых документов вводим устойчивые виртуальные buckets:

```text
bucket = stable_hash(document_id) % 16
directory[(tenant_id, bucket)] = (physical_shard, routing_epoch)
document version and command_id stored with document
router sends command with directory epoch
shard accepts writes only for its active ownership epoch
move: copy snapshot -> catch up change log -> fence old writer -> activate new
retry after move keeps original command_id and expected document revision
```

Горячему tenant нужны как минимум `ceil(24000 / (2100 − 500)) = 15` независимо размещённых частей при заданном фоне. Шестнадцать buckets, равномерно распределённых по шестнадцати шардам, дают в среднем `1500 + 500 = 2000` записей/с на затронутый шард. Это расчёт возможности, а не гарантия равномерности: измеряют максимум по buckets и отдельно нагрузку одного документа. Один сверхгорячий документ всё ещё ограничен последовательным исполнителем.

Копирование не даёт права двум владельцам одновременно принимать команды. В момент передачи нужен барьер: старый владелец прекращает запись, хвост изменений и журнал команд догоняются, затем активируется новая эпоха. Устаревший router получает отказ/redirect. Авторитетная проверка эпохи должна переживать перезапуск и исключать продолжение старого владельца при partition; локальная переменная процесса этого не обеспечивает.

Проверка перемещает bucket под нагрузкой, повторяет уже подтверждённую команду на новом шарде и возобновляет старый процесс после переключения. Проверяют версии и отсутствие потерянных подтверждений. Цена — directory, scatter/gather для выборки всех документов tenant, больше соединений и сложный перенос. Транзакции между документами на разных buckets уже требуют отдельного решения; исходное условие их не обещает.

</details>

### 6. Региональная аренда разрешает глобальную публикацию

Два региона генерируют окончательные месячные отчёты. Параллельные вычисления допустимы, но за месяц должен существовать один опубликованный результат, который старый worker не может заменить. Объектное хранилище принимает обычный `PUT` по одному ключу.

```text
region A: acquire local Redis lease(report_id, TTL=30s)
region B: acquire its own local Redis lease(report_id, TTL=30s)
worker: compute report for up to 5 minutes
worker: renew lease every 10s
worker: PUT /reports/report_id/final.csv
worker: publish URL to customers
on network partition: keep working to preserve availability
```

Найдите дефект даже без истечения TTL. Измените место принятия окончательного решения, включая пробуждение старого worker после передачи аренды.

<details>
<summary>Разбор</summary>

Независимые региональные Redis не дают единого владельца: A и B могут одновременно получить локальную аренду. Даже общий lease не мешает остановленному процессу позже выполнить подготовленный `PUT`. Продление аренды лишь уменьшает вероятность такого случая, но не защищает принимающий ресурс.

Исправление отделяет вычисление от публикации. Общий согласованный каталог хранит текущую эпоху владельца и опубликованный указатель; объекты неизменяемы:

```text
coordinator grants report_id epoch=82 in durable consensus-backed state
worker writes object /reports/report_id/82/random_object_id.csv
publish TX in SAME coordinator database:
  lock report lease row; require current_epoch=82 and lease is valid
  require no final publication for report_id; insert final pointer + outbox event
COMMIT; notifications only from committed outbox
old epoch cannot publish; object garbage collection follows publication records
```

Проверка эпохи и вставка указателя должны сериализоваться с выдачей следующей эпохи. Если lease хранится в одной системе, а указатель безусловно меняется в другой, исходное окно возвращается. В этом варианте новым worker не разрешено заменять уже окончательный отчёт. Исправление опубликованного отчёта — отдельная бизнес-команда, создающая явно обозначенную редакцию.

При потере связи с координатором регион может считать и загружать неопубликованные объекты, но не подтверждать окончательную публикацию. Это осознанная цена единственности результата. Время аренды проверяется авторитетным контуром; локальные часы worker не определяют допустимость commit. Потеря ответа на публикацию разрешается чтением каталога по `report_id`, а не новым уведомлением напрямую.

Проверка включает partition регионов, паузу worker дольше TTL, передачу эпохи и два одновременных запроса publish. Видимый указатель и обязательство уведомить должны существовать в одном экземпляре. Цена — межрегиональная координация на коротком этапе публикации, уборка лишних объектов и возможный повтор вычислений. Наличие устойчивого consensus-хранилища ещё требует правильного размещения голосов и политики failover: региональный отказ не должен создавать два независимых каталога.

</details>

### 7. Автомасштабирование не умеет погашать долг

Очередь преобразования документов до пика пуста. Поток скачком растёт до 1800 задач/с. Есть шесть workers по 200 задач/с; это уже безопасная измеренная скорость с запасом. Запуск новых workers занимает 120 секунд. База выдерживает не более 2200 завершений/с. Нужно погасить накопившийся за запуск хвост за пять минут после готовности новых workers.

```yaml
scale_metric: worker_cpu
target_cpu: 70_percent
min_workers: 6
max_workers: 40
queue_capacity: unlimited
on_database_timeout: retry_immediately
incident_resolved_when: desired_replicas_equals_ready_replicas
```

Рассчитайте требуемое число workers и исправьте управляющие сигналы. Почему масштабирование до 40 может ухудшить ситуацию?

<details>
<summary>Разбор</summary>

До масштабирования доступно 1200 задач/с. За 120 секунд копится `(1800 − 1200) × 120 = 72000` задач. Для погашения за 300 секунд нужны ещё `72000 / 300 = 240` завершений/с сверх текущего входа. Минимальная мощность — 2040, то есть `ceil(2040 / 200) = 11` workers. Они дают 2200, а фактическое погашение при постоянном входе займёт `72000 / (2200 − 1800) = 180` секунд.

```text
scale on arrival_rate, completed_rate, backlog_age and downstream saturation
desired = ceil((arrival_rate + backlog / target_drain_seconds) / 200)
effective completion ceiling = 2200/s; concurrency has its own measured limit
max useful workers for this workload = 11
admission: bounded queue; explicit rejection before durable acceptance
retry: delayed, bounded, included in the same downstream attempt budget
resolve only when oldest age and backlog return to agreed targets
```

Этот расчёт предполагает масштабирование сразу после обнаружения скачка. Каждая минута задержки добавляет ещё 36000 задач при прежней мощности. CPU может оставаться низким, когда workers ждут БД, поэтому он не измеряет ни долг, ни ограничение следующей системы. Сорок workers попробуют выдать 8000 завершений/с и способны превратить недостаток мощности в шторм таймаутов и повторов.

Верхняя граница workers не заменяет ограничение конкурентных SQL и запросов: при замедлении зависимости число одновременно занятых ресурсов меняется. Долгую очередь также нельзя считать бесплатным буфером. Если работа уже надёжно принята, переполнение обрабатывается остановкой/замедлением производителей, а не удалением подтверждённых задач. Лимит выбирают по сроку полезности, retention и месту на диске.

Проверка воспроизводит скачок, двухминутный запуск и замедление БД. Измеряют производную backlog, возраст старейшей задачи, полезные завершения и попытки отдельно. Цена — запас мощности, ранние отказы и менее агрессивное масштабирование. Если вход превысит 2200 надолго, одними workers выполнить требование невозможно: придётся ограничить вход или увеличить подтверждённую мощность БД.

</details>

### 8. Курсор обещает снимок, а хранит номер страницы

API выгружает до 100000 строк финансового отчёта порциями по 1000. За 15 минут выгрузки исходные строки могут добавляться, удаляться и менять дату. Контракт требует ровно один раз вернуть каждую строку отчёта в том виде, в котором она попала в начальный снимок. Доступ к отчёту может быть отозван во время выгрузки.

```text
GET /report?cursor=base64(page=7)
SQL: ORDER BY updated_at DESC LIMIT 1000 OFFSET page*1000
cursor has no tenant, filter hash or signature
next request opens a new database transaction
client may replace filter while retaining cursor
deleted rows disappear; updated rows move between pages
authorization checked only on first page
```

Исправьте и семантику набора, и контракт курсора. Достаточно ли заменить OFFSET на `(updated_at, id)`?

<details>
<summary>Разбор</summary>

OFFSET зависит от текущих позиций строк. Вставка перед границей даёт повторы, удаление — пропуски; одинаковые даты делают порядок неоднозначным. Составной keyset исправляет обход стабильного порядка, но не создаёт неизменяемый снимок при изменении ключа сортировки и данных. Для заданного строгого экспорта можно материализовать результат.

```text
POST /exports: authorize; create export_id and immutable query specification
builder: read one consistent source snapshot; write rows as (export_id, ordinal, payload)
mark READY only after full materialization; partial exports are not readable
cursor = sign(export_id, tenant_id, filter_hash, last_ordinal, expires_at)
GET page: reauthorize; validate cursor and export ownership
SELECT payload WHERE export_id=:id AND ordinal>:last ORDER BY ordinal LIMIT 1000
expired export -> explicit restart_required, never silently start a new snapshot
```

Материализуют значения, а не только ID: иначе изменение строки после построения списка нарушит обещанный вид отчёта. Создание снимка может идти асинхронно; до `READY` API сообщает состояние подготовки. Точный момент снимка определён запуском согласованного чтения, а не обещанием «на момент клика», если эти моменты различаются. Подпись курсора предотвращает подмену полей, но не заменяет текущую проверку прав.

Что произойдёт, если клиент записал вторую страницу и упал до сохранения следующего курсора? В тесте возьмите пять строк с номерами от 1 до 5 и размер страницы 2. После первой страницы сохранён курсор со значением 2. На повтор с этим курсором сервер должен снова вернуть строки 3 и 4 того же снимка. Это корректный повтор ответа, но обычное добавление в конец файла запишет обе строки дважды. Чтобы проверить однократный результат у получателя, сохраняйте строки и следующий курсор одной транзакцией либо делайте запись идемпотентной по ключу `(export_id, ordinal)`. Возобновите выгрузку после сбоя и проверьте, что у получателя ровно пять строк с исходными значениями.

При среднем payload 200 байт один экспорт на 100000 строк содержит около 20 МБ; сто одновременных — 2 ГБ без индексов и репликации. Это цена предсказуемой семантики. Альтернатива — длительно удерживать снимок БД, но тогда надо оценить удержание старых версий, соединений и поведение при перезапуске.

Проверка вставляет, удаляет и перемещает строки между страницами, подменяет tenant/фильтр в курсоре и отзывает доступ после третьей страницы. Частичный результат после падения builder не должен выглядеть готовым. Повторная подготовка публикуется под новым идентификатором, чтобы прежний курсор не продолжил другой снимок. Опасное исправление — только добавить `id` в сортировку: оно устраняет равные ключи, но не живую смену набора.

</details>

### 9. Миграция требует одновременного обновления всех экземпляров

У клиента есть обязательная колонка `phone`. Новый API разрешает несколько телефонов с одним основным. Rolling deployment занимает 30 минут, старые экземпляры продолжают менять `phone`. Требуется возможность откатить бинарник сутки после выпуска без потери основного телефона.

```text
migration: create customer_phones(customer_id, phone, is_primary)
backfill: copy all customers.phone once
new binary: read and write only customer_phones
old binary: keep reading and writing customers.phone
migration: drop customers.phone immediately
rollback: recreate customers.phone using first row from customer_phones
release gate: all pods have new image
```

Предложите этапы совместимости и конкретные ограничения данных. Когда разрешено включить несколько номеров и удалить старую колонку?

<details>
<summary>Разбор</summary>

Здесь одновременно нарушены совместимость бинарников и синхронизация данных. Старый процесс после разового backfill запишет новое значение только в старую колонку. Новая версия его не увидит; удаление колонки дополнительно сломает работающий запрос. Выбор «первого» номера при откате не восстанавливает понятие основного.

```text
expand: add customer_phones with UNIQUE(customer_id, phone)
constraint: at most one primary per customer; legacy phone remains authoritative
install DB-side synchronization: legacy update -> replace primary atomically
backfill: lock customer row, reread current phone, fill missing primary in same TX
deploy compatible code: primary mutations still enter through legacy phone
after old writers gone: enable additional non-primary phones; keep primary projection
after rollback window + reader/writer audit: remove compatibility path, then old column
```

В PostgreSQL ограничение «не больше одного основного» можно выразить частичным уникальным индексом по `customer_id` с условием `WHERE is_primary`. Наличие хотя бы одного номера для обязательного телефона обеспечивается транзакционным протоколом изменения и проверкой инварианта, а не этим индексом. Удаление основного и назначение другого выполняются одной транзакцией с блокировкой клиента.

Пока допустим старый бинарник, основное значение обязано иметь совместимое представление в `customers.phone`. Дополнительные номера можно включить после ухода старых writers, если при откате они сохраняются в новой таблице, а старый код меняет только основной. Важно, чтобы совместимый путь синхронизации продолжал работать и при откате: иначе сутки объявленного окна существуют только в release notes.

Backfill не должен безусловно переносить снимок, прочитанный час назад. Блокировка и повторное чтение актуального значения защищают именно эту небольшую миграцию; большие пакеты ограничивают, чтобы не удерживать множество клиентских строк.

Проверяют старый и новый бинарники одновременно, изменение телефона посередине backfill, удаление основного и реальный откат после добавления второго номера. Сравнивают значения, а не только число строк. Цена — временная двойная модель, дополнительная запись и эксплуатация синхронизации. Завершение rollout по образам недостаточно: старые batch jobs, consumers и административные скрипты тоже могут писать прежнюю колонку.

</details>

### 10. Импорт изображения получил полномочия внутреннего сервиса

Пользователь указывает URL аватара. Сервис должен принять публичное изображение до 10 МиБ, проверить его и лишь затем опубликовать. У worker есть доступ к внутренней сети и учётные данные для записи в общий bucket. Инварианты: URL не открывает внутренние ресурсы, файл другого tenant нельзя перезаписать, непроверенный объект недоступен клиентам.

```text
API: enqueue(user_supplied_url, tenant_id, original_filename)
worker: reject URL using a short hard-coded substring deny-list
worker: HTTP GET with automatic redirects and environment proxy settings
worker: read entire response into memory; trust Content-Type=image/png
worker: PUT public-bucket/{tenant_id}/{original_filename}
worker: return public URL before malware/image decoding checks
network policy: allow all egress
```

Какие границы нужно изменить? Предложите проверяемый путь данных, а не только более длинный список запрещённых строк.

<details>
<summary>Разбор</summary>

Строковая проверка не покрывает альтернативные адреса, IPv6, DNS rebinding и перенаправление на внутренний ресурс. Заявленный MIME-тип не доказывает формат файла, а чтение без лимита позволяет исчерпать память. Пользовательское имя в пути создаёт риск коллизий и перезаписи; публичная публикация до проверки делает последующий отказ запоздалым.

```text
API: authorize tenant; allocate server-generated upload_id and quarantine key
fetcher: isolated network, no application credentials, approved egress proxy only
proxy: HTTPS only; resolve/validate all addresses; block internal/special ranges
proxy: connect to validated destination; redirects disabled; bounded DNS/connect/total time
stream: abort after 10 MiB; store private quarantine object under upload_id
validator: bounded decoding, dimensions/pixel limits, format policy, required scans
publisher: copy approved result to immutable tenant-scoped key; then mark READY
```

Проверка адреса и реальное подключение должны использовать согласованное разрешение: повторный скрытый DNS lookup после проверки возвращает окно подмены. Для произвольных публичных URL deny-list остаётся сложной защитой; egress proxy и сетевые ограничения нужны независимо от приложения. Если бизнес допускает ограниченный набор источников, allow-list заметно упрощает модель.

Состояния `PENDING/SCANNING/READY/REJECTED` хранятся устойчиво. Падение после копирования, но до `READY` оставляет непоказанный объект для сверки; повтор publisher использует тот же `upload_id`. Падение сканера не открывает quarantine. Worker не получает права читать чужие объекты или публиковать произвольные ключи; отдельный publisher принимает только запись одобренного upload_id. Для прямого скачивания клиенту выдают доступ только после проверки текущих прав на объект.

Проверка использует заглушки resolver и транспорта с категориями `PUBLIC_ALLOWED` / `NONPUBLIC_DENIED`, небольшие потоки без Content-Length и искусственно сниженные пределы размера и декодирования. Одинаковые синтетические имена разных tenants не должны приводить к перезаписи. Цена — отдельный сетевой контур, хранение quarantine, задержка обработки и уборка осиротевших объектов. Замена blacklist одной регуляркой эту цену не устраняет: она оставляет сервис посредником с избыточными сетевыми полномочиями.

</details>

### 11. Метрики стали базой персональных событий

Нужно видеть latency и ошибки 20 маршрутов в двух регионах. Работают 30 экземпляров. За сутки обращаются миллион пользователей; каждого в среднем обслуживают три экземпляра. Требование — диагностика без персональных данных в метриках. Команда предлагает одну классическую histogram с десятью конечными границами бакетов.

```text
metric: http_request_duration_seconds
labels: user_id, email, request_id, raw_url, pod, region, status
raw_url example: /customers/781/cards/551?token=...
histogram observed for every HTTP response
retention: 30 days
dashboard: group by email to find slow customers
scrape success is the only monitoring-health alert
```

Оцените хотя бы нижнюю полезную границу числа рядов и предложите новую схему наблюдаемости. Какие идентификаторы куда перенести?

<details>
<summary>Разбор</summary>

Даже если убрать `request_id`, email, URL, status и регион из расчёта, миллион пользователей на трёх экземплярах даёт три миллиона реально встреченных сочетаний `(user_id, pod)`. Классическая histogram с десятью конечными бакетами имеет ещё `+Inf`, `_sum` и `_count`: 13 рядов на сочетание, то есть 39 млн рядов. Это оценка для заданных посещений, а не произведение всех теоретических значений labels. Уникальный `request_id` делает рост ещё хуже и превращает агрегат в журнал отдельных запросов.

```text
histogram labels: route_template, method, status_class, region
bounded values: 20 routes, 2 methods, 3 status classes, 2 regions
pod identity supplied by scrape target; 30 pods total across both regions
logs: trace_id and error_code; restricted, sampled, scrubbed; no URL secrets
traces: sampled spans for individual slow requests, with controlled attributes
alerts: user-visible errors/latency plus scrape gaps, ingest failures, series growth
```

Считаем новый верхний порядок: регион уже определяется размещением pod, поэтому нельзя бездумно умножать его ещё раз. Если каждый из 30 pods обслуживает все 20 маршрутов, два метода и три класса статуса, получится `20 × 2 × 3 × 30 × 13 = 46800` рядов для этой histogram. Это всё ещё бюджет, который надо сравнить с остальными метриками и реальными лимитами платформы.

`/customers/{customer_id}/cards/{card_id}` — ограниченный шаблон маршрута; неизвестные пути объединяют в фиксированную категорию, иначе fallback создаст новую кардинальность. Для расследования отдельного запроса используют trace ID и защищённые журналы. Перенос email в лог без удаления секретных query parameters не исправляет приватность.

Проверка прогоняет миллион разных ID, контролирует число уникальных series, память exporter и размер scrape. Отдельно проверяют отсутствие email и токенов в экспортируемом тексте. Цена — менее подробные агрегаты на пользователя, настройка семплирования и политика хранения диагностических данных. Успешный scrape не доказывает, что нужные события наблюдаемы.

</details>

### 12. Один бюджет повторов существует в четырёх конфигурациях

Цепочка API → service → SDK → внешний расчёт тарифа читает данные без побочного эффекта. Общий deadline — 900 мс. Зависимость допускает 2400 вызовов/с, первичный поток — 2000/с. Все значения `attempts` ниже включают первую попытку. После временного отказа пользователю нужен быстрый ответ либо явная ошибка.

```yaml
mobile_client: {attempts: 2, per_attempt_timeout_ms: 900}
api_gateway: {attempts: 3, per_attempt_timeout_ms: 800}
pricing_service: {attempts: 2, per_attempt_timeout_ms: 600}
provider_sdk: {attempts: 3, per_attempt_timeout_ms: 200}
retry_statuses: [all_errors]
backoff: exponential_without_global_limit
deadline_propagation: disabled
```

Исправьте конкретные настройки, учитывая запас всего 400 вызовов/с. Кто владеет повтором и как доказать верхнюю границу нагрузки?

<details>
<summary>Разбор</summary>

Предельное усиление исходной цепочки — `2 × 3 × 2 × 3 = 36` попыток на логический запрос, то есть до 72000 вызовов/с. Реальное число зависит от тайминга и дедлайнов; в исходном проекте единого дедлайна нет, поэтому рассчитывать на него как на защиту нельзя. Exponential backoff разносит попытки, но не задаёт общего предела.

```text
mobile and gateway: one automatic attempt for this endpoint
pricing_service: sole retry owner, at most 2 provider attempts total
provider_sdk: attempts=1; connect+request bounded by remaining deadline
end-to-end deadline: 900ms; first attempt budget <=300ms
retry only classified transient failures, with jitter and enough remaining time
retry token bucket: refill=200/s, capacity=100, initially at most 100 tokens
all provider traffic also passes a 2400/s admission limiter with defined burst
```

При устойчивых 2000 первичных вызовах и расходе повторов 200/с поток составляет не более 2200/с в среднем. Полный bucket разрешает дополнительно 100 повторов немедленно: в интервале длины `t` секунд число повторов ограничено `200t + 100`, а не строго 200 в каждом секундном окне. Поэтому общий limiter обязан иметь собственный согласованный burst, и предел провайдера следует уточнить как rate с burst либо точное окно. При буквальном жёстком ограничении в любом окне одной секунды выбирают подходящий rolling-window admission.

Отмена ожидания не гарантирует, что уже принятый провайдером вызов прекратился. Входящие после deadline запросы отбрасываются до отправки, а число in-flight ограничивается отдельно. Ошибки валидации не повторяют; массовые `429` уважают контракт провайдера, не превращая их в бесконечное ожидание.

Проверка создаёт быстрые ошибки, зависание и восстановление, затем сравнивает логические запросы с фактическими попытками на границе провайдера. Проверяют и скрытые ретраи SDK/proxy. Цена — часть запросов получит ошибку, хотя дополнительная попытка могла бы помочь; это сохраняет мощность остальным.

</details>

### 13. План восстановления начинается с недоступного ключа

Полностью потерян основной регион, включая его IAM/control plane и систему секретов. Копии БД находятся во втором регионе, но зашифрованы ключом, доступным только через первый. Требования: RPO не больше пяти минут, RTO 90 минут. БД — 600 ГБ; измеренная скорость восстановления 250 МБ/с, WAL — ещё десять минут, проверка и включение трафика — 20 минут. Единицы десятичные.

```text
backup: full nightly, stored in region B
WAL archive: hourly upload batch
encryption key: region A only
restore credentials: stored in production Vault in region A
runbook: fetch key -> restore latest backup -> replay WAL -> switch DNS
external deliveries: automatically replay all outbox rows after restore
last drill: successfully listed backup filenames
```

Покажите исправленный план с проверяемыми RPO/RTO. Какие зависимости должны пережить отказ отдельно от самих файлов копии?

<details>
<summary>Разбор</summary>

Доступная копия без ключа и полномочий восстановления не является доступным восстановлением. При полной потере A первый шаг исходного runbook невыполним. Часовая отправка WAL также не соответствует пятиминутному RPO: последние подтверждённые изменения могут отсутствовать в другом регионе почти час.

```text
independent recovery account in B: tested credentials, MFA/break-glass procedure
backup decryption capability survives loss of A; keys and permissions tested in B
continuous WAL shipping; alert on durable archive gap with margin below 5 minutes
restore network, DB, service secrets and routing from B-owned recovery resources
restore to declared point; keep outbound delivery disabled
reconcile external effects and durable operation IDs; then enable controlled traffic
record drill timestamps and recovered business watermark, not just backup success
```

Расчёт копирования: `600000 / 250 = 2400` секунд, то есть 40 минут. С WAL и проверкой получается 70 минут. На обнаружение, принятие решения, получение доступа и подготовку остаётся только 20 минут из RTO 90. Такой бюджет возможен лишь при заранее подготовленной инфраструктуре и измеренной процедуре; это ещё не доказательство фактического SLA.

Нужна непрерывная цепочка WAL от базовой физической копии до выбранной точки. Нельзя заменить её несколькими «последними файлами». Контрольная бизнес-операция с устойчивым ID позволяет проверить фактическую границу потери данных, а не только время последнего объекта в bucket.

Откат БД не откатывает уже отправленные письма, выплаты и отгрузки. После восстановления outbox может содержать ранее доставленные, но ещё не отмеченные сообщения; нужны прежние operation IDs, идемпотентные получатели и сверка неизвестных результатов. Новые ID при replay дадут повторный эффект.

На учении блокируют все зависимости A, поднимают сервис в B, выполняют чтение и запись через API, сверяют журнал внешних операций. Цена — независимые ключи/доступ, резерв инфраструктуры и регулярные полноценные учения. Нельзя честно объявить RTO выполненным по скорости копирования либо успешному `LIST` хранилища.

</details>

### 14. Кэш авторизации переживает отзыв доступа

Сотрудник открывает конфиденциальные документы разных организаций. После успешного отзыва членства каждый новый запрос должен быть запрещён. Запрос, который уже прошёл проверку до отзыва, может завершиться. Сервис авторизации доступен через согласованное хранилище, но иногда недоступен. Ответы документов кэшируются для ускорения.

```text
cache key = document_id
on cache hit: return full cached response immediately
on miss: check membership from local cache with TTL=30 minutes
membership cache key = user_id
authorization unavailable: allow if user ever had access
GET object URL: valid for 24 hours, usable without further checks
revoke: update membership database; publish best-effort invalidation
```

Найдите утечки между организациями и после отзыва. Предложите контракт кэширования, который действительно выполняет заявленное условие.

<details>
<summary>Разбор</summary>

Проверка только при промахе превращает попадание в кэш в обход авторизации. Ключ `user_id` смешивает решения для разных организаций и действий; когда-то выданное разрешение не является текущим. Лучшее TTL не выполняет немедленный отзыв, а best-effort invalidation оставляет окно потери сообщения. Длительная ссылка продолжает работать вообще без обращения к API.

```text
every request: authenticate; resolve document tenant from authoritative metadata
authorize(user, tenant, document, action) through current consistent policy state
authorization unavailable -> deny/temporary error; never reuse an unvalidated allow
then lookup content cache[(tenant, document_id, content_revision, representation)]
personalized response: cache additionally by permission projection, or build after read
download: authenticated gateway reauthorizes each new request; no long-lived bearer URL
revoke returns success only after authoritative policy commit
```

Контентный кэш может быть общим для имеющих право читателей, если в нём нет уже собранных персональных полей и проверка всегда предшествует выдаче. Сами ID в URL и подпись ссылки не доказывают действующее право. Предварительно выданная ссылка на 24 часа несовместима с требованием; даже минутная лишь ограничивает окно нарушения. Посредник скачивания должен проверять новый запрос, а приватное объектное хранилище не должно иметь обходного публичного пути.

Сервис авторизации также не может скрыто использовать устаревший `allow`: нужен согласованный контракт чтения после отзыва, включая сетевые разделения и failover. Практическая альтернатива с локальными решениями — согласиться на ограниченное окно отзыва и надёжную доставку изменений, но это изменение требования. Для исходного условия цена — дополнительная проверка на каждый запрос и потеря доступности защищённого чтения при недоступности авторитетного состояния.

Проверка прогревает кэш пользователем A, запрашивает тот же ID пользователем B другой организации, отзывает A и повторяет GET и скачивание. В аудите фиксируют решение и версию политики без содержимого документа. Уже переданные байты невозможно отозвать; условие ограничено новыми запросами и не обещает удалённое стирание скачанного файла.

</details>
