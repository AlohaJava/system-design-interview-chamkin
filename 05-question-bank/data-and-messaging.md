## Репликация, свежесть и координация

### 1. Реплика сохранила WAL: почему SELECT всё ещё возвращает старые данные?

Получить, надёжно записать и применить журнал — разные этапы. Подтверждение remote flush означает, что WAL переживёт оговорённый отказ подтвердившей реплики. Для SELECT нужны replay изменений и snapshot, включающий их. Даже успешно применённый новый commit не появится в старом snapshot уже открытой транзакции.

Например, заказ зафиксирован на primary, standby подтвердила запись WAL на диск, но её replay остановлен тяжёлым запросом или восстановлением. Приложение сразу отправляет туда `SELECT` и не находит заказ. Durability соблюдена, read-your-writes — нет. В PostgreSQL при настроенных synchronous standbys `synchronous_commit=on` и `remote_apply` различаются именно требуемым этапом подтверждения. При `remote_apply` речь идёт о выбранных synchronous standbys, а не о любой реплике в пуле.

Практическое решение — читать с актуального primary либо ожидать нужную replay-позицию на конкретной standby, затем начинать новое чтение. Ожидание ограничивают таймаутом и fallback. Ошибка — назвать любую «синхронную реплику» немедленно свежей и распространить её гарантию на весь кластер. См. [sync и async](../01-building-blocks/databases.md#sync-vs-async-репликация).

### 2. Как обеспечить read-your-writes без всех чтений с primary?

Верните вместе с успешной записью токен минимальной версии и используйте его при последующем чтении. Роутер выбирает реплику, которая уже применила эту версию, либо ждёт её догонки, либо обращается к primary. Токен — логическая позиция/версия, а не время на часах клиента.

Например, после изменения профиля API возвращает `profile_version=42`. Запрос с `min_version=42` нельзя обслужить значением 41. Для конкретной БД можно использовать позицию журнала, полученную после commit; при этом нужно знать, относится ли позиция к той же истории репликации. После failover старый LSN без timeline/epoch нельзя автоматически сравнивать с новой историей. Для нескольких независимых шардов одного скалярного токена может быть недостаточно.

Sticky routing уменьшает вероятность stale reads, но закрепление за отставшей репликой не заставляет её догнать запись. Чтение с primary тоже предполагает, что это действующий лидер и его история содержит подтверждённый commit. Фиксированное правило «пять секунд читать с лидера» — эвристика, а не гарантия при произвольном lag. Нужны измеримый barrier и определённое поведение при его недостижении. Контекст — [аномалии async](../01-building-blocks/databases.md#что-ломается-при-async-аномалии-которые-спрашивают).

### 3. Чем отличаются linearizability, Serializable и ACID consistency?

Linearizability описывает операции над объектом как единую копию и сохраняет порядок реального времени: завершённая запись предшествует чтению, начатому позже. Serializable описывает транзакции: результат эквивалентен некоторому последовательному выполнению. Обычная serializability сама по себе не требует, чтобы этот порядок совпадал с реальным временем. Сочетание serializability с таким требованием называют strict serializability.

ACID consistency — ещё один смысл слова: транзакции сохраняют заданные инварианты данных. Например, constraint не допускает отрицательный остаток. Его существование не означает, что любой запрос с async-реплики видит самый новый остаток. И наоборот, linearizable `GET`/`SET` не превращают пару отдельных операций `GET balance` → `SET balance-10` в атомарное списание.

Для последнего товара полезен один условный `UPDATE ... WHERE stock > 0` с проверкой числа изменённых строк либо правильно изолированная транзакция. Для инварианта между несколькими строками может понадобиться Serializable с повтором всей транзакции при конфликте. Ошибка — сказать «у нас ACID, значит никаких гонок и stale reads нет». Уточняйте единицу атомарности, изоляцию и источник чтения отдельно.

### 4. Почему R + W > N ещё не гарантирует корректный счётчик?

Неравенство даёт пересечение множеств реплик чтения и успешной записи при одной фиксированной конфигурации. Оно не делает атомарной последовательность «прочитать, вычислить, записать» и не выбирает бизнес-корректный результат конфликтующих обновлений.

Пусть `N=3`, `R=W=2`, баланс 100. Два клиента читают 100 и независимо списывают 10, записывая 90. Обе записи могут получить два ACK, включая ACK общей реплики. Итог 90 вместо 80: пересечение состоялось, но lost update остался. `W>N/2` означает пересечение любых write quorums, а не взаимное исключение писателей.

Для инкремента нужен атомарный primitive с подходящей семантикой либо conditional write/CAS, сериализующий конфликтующие изменения. Cassandra LWT использует отдельный протокол Paxos; обычный QUORUM не заменяет его. Сравнение версий тоже требует понятного правила: timestamp с быстрых часов может победить более позднюю по реальному времени запись.

Ошибка — переносить геометрическое свойство множеств на изоляцию транзакций. На интервью явно перечислите предпосылки: те же N реплик, корректное версионирование, правила обработки конкурентных и незавершённых записей, отсутствие неподконтрольной смены состава. Дальше — [кворумы](../01-building-blocks/cap-and-consistency.md#кворумы-r--w--n).

### 5. Что происходит, если запись получила таймаут после подтверждения части реплик?

Таймаут не равен rollback. Клиент знает только, что не получил окончательный ответ; запись могла не выполниться, выполниться полностью либо сохраниться на части реплик и повлиять на будущие чтения. Возможные истории определяются протоколом конкретной СУБД.

Например, координатор послал запись трём репликам, две её сохранили, но ответ клиенту потерялся. Повтор с новым ID создаст второй заказ. Безопасный повтор использует тот же бизнес-идентификатор и атомарное условие уникальности. Для денежной операции дополнительно нужен стабильный idempotency key получателя. Чтение сразу после таймаута помогает расследованию, но его отрицательный ответ не доказывает отсутствие записи, если маршрут допускает stale reads.

В API полезно различать «завершено», «отклонено» и «исход неизвестен». Последний вариант возвращает `operation_id`, по которому можно запросить статус и продолжить восстановление. Не нужно подтверждать клиенту отказ, одновременно запуская неконтролируемую новую операцию: позднее завершение старой даст дубль.

Частая ошибка — бесконечно повторять любую ошибку с новым UUID. Повторы должны сохранять идентичность операции, иметь deadline и использовать протокол восстановления неопределённого результата. См. [идемпотентные потребители](../01-building-blocks/distributed-transactions.md#идемпотентные-консьюмеры).

### 6. В чём практический смысл CAP на примере регистрации email?

Если глобальная уникальность email обязательна, две изолированные стороны не могут независимо подтвердить регистрацию одного адреса и одновременно гарантировать, что подтверждение получит только одна. Нужен общий сериализующий арбитр, владелец диапазона email либо заранее распределённые права на значения. Во время partition часть запросов не сможет завершиться успешно.

Сценарий: регионы A и B не видят друг друга, в обоих отсутствует `x@example.org`, два клиента одновременно регистрируются. Локальные `UNIQUE(email)` защищают только свои базы. Асинхронная репликация позже обнаружит конфликт, но уже выданные два подтверждения не становятся одним. Можно принять заявку со статусом `PENDING`, но это другой контракт: регистрация ещё не гарантирована.

В формальной CAP C — linearizability, A — завершение каждого запроса к неотказавшему узлу; A не является обещанием p99 меньше 200 мс. Ошибка — рассуждать «у нас SQL, поэтому CA» или считать ответ «недоступно» сохранением CAP availability. Для дизайна важнее описать поведение конкретной операции и момент выдачи обязательства пользователю. Подробнее — [CAP](../01-building-blocks/cap-and-consistency.md#cap-теорема-простым-языком).

### 7. Почему выбор нового лидера не решает split brain сам по себе?

Выборы определяют, кто должен быть лидером, но старый процесс может не узнать о потере роли: GC-пауза, зависший heartbeat или partition не выключают его физически. Если ресурс продолжает принимать команды старого владельца, две истории могут развиваться параллельно.

Например, воркер A получил lease и начал обновлять файл, завис на минуту; lease истёк, B стал владельцем и записал новую версию. A проснулся и отправил отложенную запись. Проверка lease перед паузой уже бесполезна. Fencing token — монотонный epoch владельца — передаётся с каждой записью, а **сам защищаемый ресурс** атомарно отвергает token старее принятого. Проверка только в приложении оставляет окно между проверкой и действием.

Consensus-система должна безопасно выдавать epochs, а хранилище — поддерживать их применение. Случайный UUID lock-owner помогает безопасно удалить только свой lock, но не задаёт порядок владельцев и не является fencing token. Для внешнего API без поддержки fencing используют доступные conditional operations, идемпотентный контракт или последовательного владельца с иными ограничениями. Ошибка — считать TTL автоматической отменой уже отправленного I/O.

### 8. Репликация защищает от потери данных: зачем тогда бэкапы?

Репликация быстро распространяет изменения, включая ошибочные `DELETE`, повреждённые бизнес-значения и последствия взлома. Она повышает доступность текущего состояния, но обычно не предоставляет независимую историю, из которой можно восстановить состояние до ошибки.

Например, скрипт удалил все заказы и через секунду удаление применили все standby. Переключение на реплику не поможет. Для восстановления нужны проверенный base backup и непрерывный архив WAL до нужной точки, а также отдельный доступ к ним. Восстановление делают на изолированный экземпляр, проверяют инварианты, затем выбирают безопасный способ возврата данных: полное переключение либо выборочное восстановление. Последний вариант требует учесть новые легитимные записи после инцидента.

RPO — допустимая потеря данных по времени/объёму; RTO — время восстановления сервиса. Синхронная репликация может уменьшить RPO при отказе машины, но не отменяет RTO failover и человеческих ошибок. Ошибка — обещать «ноль потерь» без модели отказов, географии копий и теста восстановления. Проверять надо успешность restore, ключи шифрования и полноту цепочки журнала, а не только зелёный статус backup job.

### 9. Чем read repair, hinted handoff и anti-entropy отличаются друг от друга?

Они чинят рассогласование разными путями. Read repair обнаруживает разные версии во время чтения и согласует затронутые реплики по правилам продукта. Hinted handoff сохраняет намерение передать пропущенное изменение временно недоступной реплике. Anti-entropy периодически сравнивает наборы данных и восстанавливает расхождения, включая ключи, которые никто не читает.

Пусть одна реплика была недоступна при изменении редко используемого профиля. Трафик чтений этот профиль не затрагивает: read repair не запускается. Hint может помочь после короткого отказа, но его срок хранения ограничен. Тогда нужна плановая repair-процедура. Наличие одной техники не заменяет остальные и не освобождает от мониторинга.

Удаления особенно чувствительны к срокам хранения tombstones и возврату сильно отставшей реплики. Если информация об удалении уже очищена, старая копия может воскресить данные. Конкретные риски зависят от СУБД и настроек repair/GC. Ошибка — сказать «eventual значит само сойдётся» без описания того, кто доставит пропущенные изменения и какие данные ещё доступны для восстановления.

### 10. Как сформулировать измеримую гарантию свежести вместо «обычно лаг маленький»?

Разделите эксплуатационный SLO и контракт чтения. SLO «99,9% обновлений видны в поиске за 5 секунд» измеряет типичную работу. Контракт bounded staleness требует не отдавать данные старее разрешённой границы: при нарушении система должна ждать, переключиться на другой источник или вернуть определённую ошибку.

Например, карточка товара допускает stale-описание до минуты, а checkout обязан проверить текущую цену и остаток у источника истины. Если CDC остановился на десять минут, продолжение чтений из поиска нарушит контракт, даже если месяц до этого lag был 100 мс. Возраст последнего обработанного события полезен, но при отсутствии новых записей не всегда означает реальное отставание. Нужны source position/heartbeat и сопоставление с применённой позицией.

Часы разных машин добавляют неопределённость при измерении возраста, поэтому для причинной свежести лучше версии и позиции. Контролируйте p99 lag, возраст самой старой необработанной записи, долю fallback и таймауты ожидания. Ошибка — назвать мониторинг доказательством гарантии: алерт сообщает о нарушении, а гарантию обеспечивает поведение read path при его обнаружении. Контекст — [модели консистентности](../01-building-blocks/cap-and-consistency.md#спектр-моделей-консистентности).

## Шарды, ключи и перенос данных

### 11. Как выбрать shard key, если данные распределены ровно, а нагрузка — нет?

Нужно оценивать распределение байтов, запросов и стоимости операций отдельно. Миллион одинаковых по размеру профилей может делиться идеально, но один популярный профиль получать половину чтений. Хэш равномерно раскладывает ключи, а не запросы внутри одного ключа.

Начните с доминирующих access patterns и инвариантов. Для истории чата `chat_id` обеспечивает локальное чтение и последовательную запись сообщений; гигантский публичный канал может стать исключением. Если перегружены чтения, сначала подходят кэш, реплики и объединение одинаковых запросов. Если записи независимы, возможны buckets `(chat_id, bucket)`; если требуется строгая последовательность всего чата, разделение потребует дополнительного sequencer или изменения контракта.

Перед выбором соберите распределение QPS и размеров по ключам, p99 на самом горячем шарде, рост крупнейшего tenant и нагрузку при отказе. Обсудите цену нового ключа: сколько шардов затронет обычный запрос и можно ли проверить нужные constraints локально. Ошибка — считать `user_id` заведомо хорошим, потому что у него высокая cardinality. Она необходима для распределения, но не доказывает равномерность нагрузки. Подробнее — [выбор shard key](../01-building-blocks/sharding.md#выбор-shard-key).

### 12. Почему связанные таблицы недостаточно просто шардировать по одному полю?

Для локальных JOIN и транзакций нужны одинаковая функция распределения, совместимая карта владельцев и общий ключ группировки. Одинаковое название колонки само по себе colocating не обеспечивает.

Например, `orders(customer_id, order_id)` и `order_items(customer_id, order_id, item_id)` можно размещать по `customer_id` в одной colocated-группе. Создание заказа с позициями тогда укладывается в локальную транзакцию. Если вторую таблицу независимо распределить по `order_id`, она может оказаться на другом шарде даже при наличии `customer_id`. Нужен контракт роутинга, а не просто дублированное поле.

У модели есть цена: список заказов покупателя локален, а глобальный поиск заказа только по `order_id` потребует directory/index либо ID с информацией о маршруте. Перенос покупателя между шардами должен переносить все относящиеся к нему таблицы согласованно. Межклиентские операции всё равно остаются распределёнными.

Ошибка — сказать «все данные одного пользователя вместе, значит cross-shard транзакций больше нет»: перевод между двумя пользователями нарушает это предположение. Иногда границу агрегата лучше изменить, но нельзя спрятать межагрегатный инвариант переименованием ключа. См. [cross-shard транзакции](../01-building-blocks/sharding.md#cross-shard-транзакции).

### 13. Как сохранить глобальную уникальность email после шардирования по user_id?

Локальный `UNIQUE(email)` действует только в своей области проверки. Если одинаковые email могут попасть на разные шарды, общего ограничения он не создаёт. Генерация глобально уникального `user_id` решает уникальность ID, но не email.

Один вариант — отдельный registry `normalized_email → user_id`, распределённый именно по нормализованному email и поддерживающий атомарный insert-if-absent. Сначала резервируется адрес с `registration_id`, затем создаётся пользователь. Между шагами возможен сбой: reservation должен иметь durable-статус и процедуру завершения/освобождения, проверяющую владельца операции. Слепое удаление reservation по TTL может освободить адрес уже созданного пользователя при запоздавшем ответе.

Другой вариант — распределённый unique index/транзакция поддерживаемой СУБД либо изменение shard key под уникальное значение. Для каждого решения нужны правила нормализации и изменения email, а также поведение при partition. До согласования владения адресом подтверждать окончательную регистрацию нельзя, если уникальность обязательна.

Ошибка — «проверить все шарды, затем вставить»: два параллельных запроса оба увидят отсутствие адреса. Проверка и захват должны быть одной сериализованной операцией.

### 14. Почему consistent hashing не является протоколом миграции?

Алгоритм определяет, кто должен владеть ключом после изменения топологии, и уменьшает долю ключей с новым владельцем. Он не копирует данные, не синхронизирует конкурентные записи и не останавливает клиентов со старой картой кольца.

Например, добавили узел D, ключ пользователя теперь принадлежит ему, но профиль ещё на B. Немедленное обновление кольца даст пустые чтения. Если часть роутеров уже пишет в D, а часть ещё в B, простой повтор копирования может затереть новое состояние старым. Нужны snapshot и поток изменений, версии данных, write barrier/epoch, переключение владельца и обработка stale-маршрутов.

Оценка «переедет примерно 1/(N+1) данных» предполагает равномерное размещение ключей, одинаковую ёмкость узлов и добавление одного узла к N. Она не гарантирует такой же объём QPS или равный migration time: крупные значения и горячие ключи нарушают среднее. Virtual nodes снижают разброс, но сами тоже не распределяют операции одного hot key.

Ошибка — заменить план resharding словами «у нас consistent hashing, поэтому без downtime». На интервью отделите placement function от протокола передачи владения. Дальше — [ребалансировка](../01-building-blocks/sharding.md#resharding-и-ребалансировка).

### 15. Как перенести шард, пока в него продолжают писать?

Нужен момент, после которого у диапазона снова ровно один принимающий записи владелец, а новая копия содержит все подтверждённые изменения старого. Типичный протокол: согласованный snapshot с позицией журнала, CDC от этой позиции, догонка, короткий write barrier, окончательная догонка до известного watermark и смена epoch маршрутизации.

Сценарий: snapshot закончен в 12:00, CDC почти догнал в 12:05. Значение lag «0 мс» не означает, что между измерением и переключением не появилась новая запись. Поэтому фиксируют барьер и запрещают старому владельцу подтверждать новые изменения после передачи. Старые клиенты получают redirect/retry; запрос несёт версию маршрута, и хранилище проверяет её. При падении координатора шаги должны быть возобновляемыми по durable-состоянию миграции.

Старые данные удаляют после сверки, периода наблюдения и окончания окна отката. Обратное переключение после новых записей на целевом шарде тоже требует синхронизации: старый источник уже не актуален. Ошибка — считать feature flag атомарным для всех клиентов мира или использовать два независимых app dual-write без журнала восстановления. См. [resharding](../01-building-blocks/sharding.md#resharding-и-ребалансировка).

### 16. В чём цена global secondary index и когда он становится источником ошибок?

Global index размещает данные по вторичному ключу независимо от основной таблицы. Это уменьшает fan-out чтения, но изменение объекта может затрагивать две разные области хранения. Если индекс обновляется асинхронно, он может временно пропускать существующий объект или ссылаться на удалённый.

Например, заказы шардированы по `customer_id`, а поддержка ищет по `payment_reference`. Индекс `payment_reference → (customer_id, order_id)` позволяет найти нужный шард. После создания заказа source commit уже успешен, а индекс ещё не обновлён: ответ «не найдено» не доказывает отсутствие заказа. Если такая проверка используется для защиты от повторного списания, бизнес-инвариант сломан. Уникальность нельзя обеспечивать eventually consistent индексом без дополнительного протокола.

Для пользовательского поиска можно принять lag, перепроверять найденные объекты в основной БД и показывать известное ограничение свежести. Для строгого lookup нужны поддерживаемый транзакционный индекс, registry либо чтение источника истины. План восстановления включает полный rebuild и сопоставление версий. Ошибка — считать любой инвертированный индекс глобальным: в Elasticsearch индекс локален шарду, а координатор обычно делает fan-out. См. [вторичные индексы](../01-building-blocks/sharding.md#cross-shard-запросы-и-scatter-gather).

### 17. Как сделать корректную пагинацию результатов с нескольких шардов?

Для сортировки нужен полный, стабильный порядок, например `(created_at DESC, id DESC)`, а не один timestamp с возможными совпадениями. Роутер запрашивает кандидатов у шардов, сливает отсортированные потоки и выдаёт глобальную страницу. Курсор содержит последнюю пару сортировки и при необходимости позиции отдельных потоков.

Пример: три шарда возвращают локальные top-20, роутер делает merge и отдаёт глобальные 20. Следующая страница запрашивает записи строго после курсора. Это дешевле глубокого `OFFSET`, но concurrent updates могут менять результаты: запись способна переместиться через границу страниц. Для неизменяемого feed достаточно явно принять такие ограничения; для выгрузки «все записи ровно один раз» нужен согласованный snapshot/фиксированный watermark и неизменная сортировка в его пределах.

При отказе одного шарда выбор между partial results и ошибкой — часть контракта. Нельзя молча вернуть неполную страницу как полный результат. Если объекты сортируются по изменяемому score, полезны материализованный snapshot выдачи или короткоживущая поисковая сессия. Ошибка — думать, что cursor сам гарантирует snapshot consistency и устраняет пропуски при любой модификации данных. Дальше — [scatter-gather](../01-building-blocks/sharding.md#cross-shard-запросы-и-scatter-gather).

### 18. Когда партиционирование большой таблицы не ускорит запрос?

Когда план не может исключить лишние партиции или основная цена находится в другом месте. Партиционирование не заменяет индекс и не распределяет один PostgreSQL-сервер по нескольким машинам. Его сильные стороны — pruning, локальность горячих данных и управление жизненным циклом.

Например, `events` разделена по `created_at` на месяцы. Запрос `WHERE user_id=42` без ограничения времени может пройти по всем партициям и выполнить множество index scans; число планируемых объектов также растёт. Для запроса за последние сутки pruning уменьшит объём работы, если предикат сопоставим с partition bounds. Функции/преобразования над ключом и неверные типы иногда мешают ожидаемому плану — это проверяют через `EXPLAIN`.

Старый месяц можно быстро отсоединить/удалить целиком вместо массового `DELETE`, но locking и DDL-процедуру всё равно надо планировать. Ограничения уникальности зависят от СУБД: в PostgreSQL unique constraint partitioned table должен включать partition key. Ошибка — партиционировать по дате и пообещать ускорение любого запроса, больше write capacity машины и глобальный `UNIQUE(id)` без проверки возможностей продукта.

### 33. Очередь заявок сортируется по времени. Дадут ли два одиночных индекса тот же результат, что составной?

Диспетчер постоянно запрашивает первые 50 заявок одного статуса в порядке `created_at, id`. Для такого запроса B-tree по `(status, created_at, id)` позволяет перейти к нужному статусу и читать записи в нужном порядке. Последний столбец фиксирует порядок заявок с одинаковым временем. Фильтр по статусу может быть малоизбирательным, но возможность остановиться после 50 подходящих строк всё равно ценна.

С отдельными индексами по статусу и времени планировщик может выбрать проход по времени с фильтрацией либо собрать подходящие строки и отсортировать их. При редком статусе первый вариант прочтёт много неподходящих строк, при массовом — может оказаться выгодным. Сравните планы и число просмотренных строк для пустой, редкой и массовой очереди. В общую цену решения входят дополнительные записи в индекс при приёме заявки и смене статуса.

### 34. Товар подорожал. Какую цену должен показать старый чек?

У факта продажи и текущей цены в каталоге разный срок жизни. В строке заказа сохраните согласованные сумму, валюту, количество и применённую скидку в объёме, нужном для воспроизведения чека. Например, две упаковки по 90 рублей со скидкой 10 рублей на всю строку дают 170 рублей. Следующая цена каталога, 110 рублей, эту сумму не меняет. Ссылка на неизменяемую и сохраняемую версию предложения тоже годится, если по ней всегда можно восстановить эти значения.

Отделите историю от копии ради ускорения: исправленное название в поисковой карточке можно переиндексировать, а зафиксированную продажу нельзя пересчитать из нового каталога. Корректировка прошедшей продажи должна иметь собственную запись и связь с исходной. Проверка проста: смените цену и скидку в каталоге, выгрузите вчерашний чек повторно и сравните сумму с проведённой оплатой.

### 35. Ночной отчёт по всем заказам тормозит оформление покупок. Куда перенести чтение?

Точечные записи и большие сканирования конкурируют за диск, память и процессор. Сначала проверьте план и объём работы: запросу за один день может хватить ограничения диапазона. Если отчёт регулярно сканирует большую долю истории, выделите для него реплику либо выгрузку в аналитическое хранилище. На выделенной реплике остаётся нагрузка от применения изменений, а задержка данных изменит смысл отчёта.

Определите, что означает «выручка за вчера»: по времени продажи или по времени её появления в отчётной системе, что делать с опоздавшим возвратом. Покажите пользователю границу полностью обработанных данных; текущее время окончания запроса её не заменяет. Проверяйте решение на заказе возле полуночи и возврате, который поступил утром. Если итог подлежит исправлению, повторная сборка того же интервала должна заменять прежнюю версию результата без двойного учёта.

### 36. Для поиска по словам в описании товара уже есть B-tree по строке. Почему этого может не хватить?

B-tree по полному описанию хорошо обслуживает некоторые сравнения строки целиком. Покупатель же ищет слова, которые встречаются в произвольном месте, иногда в другой грамматической форме. При таком контракте обычно строят обратный индекс: для каждого обработанного термина сохраняют документы, в которых он встретился. При поиске всех слов «зелёный чай» пересекают два списка кандидатов. Для точной фразы «зелёный чай» слова должны стоять рядом и в заданном порядке. Позиции терминов в индексе либо повторная проверка текста позволят исключить описание «зелёный байховый чай».

Уточните язык разбора, правила словоформ и выдачу при опечатках: простой индекс терминов не обещает исправлять ошибки. Сначала проверьте, хватает ли полнотекстового поиска в основной БД. При отдельном поисковом сервисе появляются задержка индексации и процедура удаления устаревших документов. Приёмочный набор должен включать разные формы слова, два слова в обратном порядке, обновление описания и удаление товара.

## Доставка, порядок и повторная обработка

### 19. Чем подтверждение публикации отличается от подтверждения обработки?

Publisher ACK сообщает о приёме/сохранении сообщения согласно политике брокера. Consumer ACK сообщает брокеру, что данную доставку можно считать завершённой. Ни одно из них само по себе не означает, что весь бизнес-процесс закончился: чек сформирован, письмо дошло адресату, деньги зачислены получателю.

Например, API записал `GenerateReport` и получил publisher confirm. Можно вернуть `202 Accepted` с `job_id`, но нельзя объявить отчёт готовым. Воркер построил файл, зафиксировал его адрес и статус `COMPLETED`, затем подтвердил обработку. Если он упал после фиксации результата до ACK, задача придёт повторно и должна найти уже созданный результат. Если ACK ушёл до сохранения файла, сбой оставит задачу потерянной для обычного механизма redelivery.

В RabbitMQ publisher confirms и consumer acknowledgements независимы: подтверждение producer не ждёт потребителя. Для end-to-end статуса нужен отдельный durable task record или результатное событие, тоже публикуемое надёжно. Ошибка — отвечать «успешно выполнено» после ACK брокера или считать подтверждение равным полной физической сохранности при любых отказах. Уточняйте режим очереди, репликацию и durability.

### 20. В каком окне появляется дубль и как его безопасно обработать в PostgreSQL?

Классическое окно — бизнес-commit уже состоялся, а consumer offset/ACK ещё не зафиксирован. После падения брокер повторит вход. Устранить это окно отдельной предварительной отметкой нельзя: появится зеркальный риск «отметили обработанным, эффект не выполнили».

Для локального эффекта используйте inbox и одну транзакцию:

```sql
BEGIN;
INSERT INTO inbox (consumer_name, event_id)
VALUES ('ledger-projector', :event_id)
ON CONFLICT DO NOTHING
RETURNING event_id;
-- Продолжаем только если INSERT вернул строку.
UPDATE accounts SET balance = balance + :delta WHERE id = :account_id;
-- Проверяем, что нужный account действительно найден.
COMMIT;
-- Только теперь подтверждаем сообщение брокеру.
```

Нужен unique/primary key по `(consumer_name, event_id)`: разные обработчики могут независимо обрабатывать один event. Если бизнес-операция падает, inbox тоже откатывается. Если commit успешен, повтор видит конфликт и пропускает эффект. Простой `ON CONFLICT DO NOTHING` без проверки результата не защищает от повторного UPDATE.

Внешний HTTP-вызов в эту транзакцию не входит; для него нужен иной протокол. Удаление inbox до окончания допустимого replay-окна вернёт риск дубля. Ошибка — разделить inbox и эффект двумя коммитами или заменить их Redis SET. Подробнее — [идемпотентные потребители](../01-building-blocks/distributed-transactions.md#идемпотентные-консьюмеры).

### 21. Где Kafka exactly-once действительно работает, а где заканчивается?

Для read-process-write между Kafka-топиками транзакционный producer может атомарно зафиксировать выходные записи и offsets входа. Downstream с `read_committed` видит только committed-результаты. Если обработчик упал до commit, вход можно прочитать и обработать заново, а предыдущий незавершённый результат не становится вторым видимым эффектом.

Пример: приложение читает `orders`, пишет `invoice-events` и передаёт входные offsets в ту же Kafka-транзакцию. Падение процесса не должно дать два committed результата для одного входа при корректном использовании протокола. Но если между чтением и commit оно вызвало HTTP `chargeCard`, Kafka не откатит платёж. Повторный запуск способен списать деньги повторно, даже когда Kafka-выход корректен. Нужны стабильный payment key и гарантия получателя.

Idempotent producer отдельно решает более узкую задачу: дедупликацию его сетевых retry, а не произвольных повторных `send` того же бизнес-события. Повторное исполнение кода допустимо при exactly-once effects; нельзя определять EOS как «функция физически запустилась единожды». Ошибка — либо обещать глобальное EOS включением флага, либо объявлять такую семантику невозможной вообще.

### 22. Почему одинаковый partition key не гарантирует порядок бизнес-эффектов?

Kafka упорядочивает записи в логе партиции, но приложение может завершить их обработку иначе. Порядок producer-вызовов, попадания в журнал и commit внешних эффектов — разные порядки. Для бизнес-последовательности их надо согласовать.

Например, `OrderCreated(v1)` и `OrderCancelled(v2)` пришли в одну партицию. Consumer запустил оба в thread pool: cancel завершился первым, затем медленный created перезаписал статус на `NEW`. Лог не нарушен, состояние заказа неверно. Решение — последовательное исполнение для одного aggregate key, проверка ожидаемой версии и state machine. Для snapshot-событий допустимо принимать только более новую версию; для дельт пропуск версии часто требует ожидания или повторного чтения источника.

Несколько producer могут одновременно писать один ключ: порядок Kafka отражает поступление к partition leader, а не обязательно бизнес-причинность. При увеличении числа партиций хэш-маршрут ключа тоже может измениться; старые и новые события окажутся в разных потоках. Ошибка — решить всё только `key=order_id` и оставить неконтролируемый параллелизм/retry. Опишите источник sequence, порядок публикации и политику применения. Контекст — [partitioning](../01-building-blocks/message-queues.md#consumer-groups-и-partitioning).

### 23. Почему перенос неудачного сообщения в retry-topic может нарушить порядок?

Основной поток продолжает движение, пока ошибка обрабатывается отдельно. Это меняет относительный порядок применения событий одного ключа, даже если внутри каждого топика записи упорядочены. Retry-topic не является продолжением той же очереди автоматически.

Например, `reserve(order=7, seq=1)` не выполнился и ушёл на минутный retry, а `ship(order=7, seq=2)` обработался сразу. Доставка заказа без резерва недопустима. Для такого процесса можно остановить обработку данного ключа, хранить ожидаемую последовательность и откладывать последующие события либо явно моделировать workflow/state machine, которая не разрешит `ship` до нужного состояния. Пауза всей партиции проста, но блокирует и другие ключи: это цена выбранной гранулярности порядка.

Если события независимы, retry-topics подходят и увеличивают пропускную способность. Нужно также надёжно связать отправку в retry и commit исходного offset: падение между двумя действиями создаёт потерю или дубль, если нет Kafka-транзакции либо отдельного durable-протокола. Ошибка — считать DLQ решением корректности: она освобождает поток, но бизнес-операция остаётся незавершённой. См. [DLQ](../01-building-blocks/message-queues.md#dead-letter-queue-и-poison-messages).

### 24. Почему commit максимального завершённого offset может потерять сообщения?

В обычной Kafka consumer group offset описывает позицию следующего чтения партиции, а не множество независимо завершённых сообщений. Продвижение через незавершённый offset означает, что после восстановления группа начнёт читать уже после него.

Пример: воркеры параллельно получили offsets 100, 101 и 102. Обработка 101 и 102 закончилась, а 100 ещё выполняется. Commit позиции 103 и последующее падение приведут к пропуску 100 при возобновлении группы. Нужно фиксировать только непрерывный завершённый префикс: пока 100 не завершён, подтверждённая позиция остаётся 100. После завершения всех трёх можно commit 103. Внутренний tracker должен учитывать ошибки, rebalance и повторное назначение партиции.

Другой вариант — быстро и атомарно переложить задачи в durable task store, затем commit входа и выполнять их независимо уже по его протоколу. Это дополнительная система, поэтому её оправдывают длительностью и параллелизмом работ. Ошибка — полагать, что Kafka хранит per-message ACK как традиционная task queue. Для стандартной consumer group надо понимать cursor-модель, а не переносить механически модель RabbitMQ.

### 25. Почему visibility timeout или consumer rebalance не исключают двух активных обработчиков?

Они управляют правом на доставку, но не отменяют уже запущенный внешний эффект старого обработчика. Процесс может зависнуть, потерять связь с брокером и продолжить работу после того, как тот отдал задачу другому.

Например, SQS-воркер A начал формировать счёт, visibility timeout истёк, воркер B получил то же сообщение. A ещё жив и позже завершает запись. Продление visibility уменьшает вероятность, но не заменяет идемпотентность и не является вечным lease. Аналогично старый Kafka consumer после rebalance может всё ещё ждать ответ банка; запрет commit старого group generation не откатывает уже принятый банком платёж.

Для локальной записи подходят unique operation ID и атомарная фиксация результата. Для ресурса с эксклюзивным владельцем нужен проверяемый fencing epoch; для внешнего API — поддерживаемый им idempotency key и запрос статуса неопределённой операции. Если обработка длительная, контролируйте heartbeat/deadline и прекращайте новую работу после потери владения, но учтите уже отправленные запросы.

Ошибка — объявить «партиция назначена одному consumer, значит дубликат физически невозможен». При распределённом исполнении схема назначения и однократность результата решают разные задачи. См. [основы очередей](../01-building-blocks/message-queues.md#базовая-модель-producer-broker-consumer).

### 26. Что на самом деле гарантирует acks=all при replication factor 3?

ACK зависит от текущего ISR, а не просто от replication factor. RF=3 задаёт число реплик партиции, но часть из них может отставать и не входить в in-sync set. `min.insync.replicas` ограничивает, при каком размере ISR запись с `acks=all` вообще разрешена.

Например, RF=3, в ISR остался один лидер. При `min.insync.replicas=1` он способен подтвердить запись без второй актуальной копии. При пороге 2 такая запись должна быть отклонена до восстановления достаточного ISR: доступность уступает durability. Конфигурация RF=3/minISR=2/acks=all — осмысленный пример для определённой модели отказов, но не обещание пережить одновременную потерю всех дисков или небезопасное избрание отставшей реплики.

Idempotence producer защищает от дублей его retry, но не сохраняет данные, которые никогда не были приняты брокером. Producer обязан обрабатывать ошибки и timeout с неопределённым исходом, а не «отправить и забыть». Для брокера также важны safe leader election, сохранность хранения и мониторинг ISR. Ошибка — переводить `all` как «навсегда записано на всех трёх дисках независимо от состояния кластера».

## Outbox, саги и изменение контрактов

### 27. Какое окно сбоя закрывает outbox, а какое оставляет?

Outbox закрывает разрыв между локальным бизнес-commit и сохранением намерения опубликовать событие. Обе строки фиксируются в одной транзакции; после её успеха durable-запись события остаётся доступной relay. Он не делает атомарными PostgreSQL commit и приём сообщения Kafka.

Пример: заказ и `OrderCreated(event_id=e7)` закоммичены. Relay публикует e7, получает ACK и падает до установки `published_at`. После восстановления e7 отправляется снова. Если отметить публикацию **до** отправки, зеркальный сбой потеряет событие. Поэтому обычный outbox даёт at-least-once публикацию при доступности relay/брокера и сохранности исходных данных, а downstream должен атомарно дедуплицировать `event_id` вместе со своим эффектом.

`FOR UPDATE SKIP LOCKED` разделяет строки между активными relay, но не отменяет окно после publish; долго держать SQL-транзакцию во время сетевой отправки тоже дорого. CDC уменьшает polling-нагрузку, но требует контроля offsets, slots и восстановления коннектора. Мониторьте возраст самой старой непереданной записи, ошибки и backlog, а не только размер таблицы. Ошибка — считать outbox мгновенной доставкой или заменой наблюдаемого процесса восстановления.

### 28. Почему BIGSERIAL и created_at в outbox не доказывают порядок событий?

Sequence выдаёт номера до commit, а транзакции способны завершаться в другом порядке. Timestamp также может фиксировать начало транзакции, совпадать у нескольких строк или зависеть от часов. Сортировка по такому полю не превращает публикацию в сериализованный бизнес-поток.

Пример: T1 получила id=100 и зависла, T2 получила id=101 и закоммитилась. Poller увидел только 101 и продвинул watermark; затем T1 закоммитила 100. Если выборка устроена как `WHERE id > last_seen_id`, событие 100 потеряется. Polling по явно неопубликованному состоянию не теряет его таким способом, но может отправить позже 101. Несколько relay с `SKIP LOCKED` могут переставить даже уже видимые строки.

Если порядок обязателен для заказа, version назначается в той же транзакции, которая сериализует изменения агрегата; `UNIQUE(aggregate_id, version)` защищает нумерацию, а relay обеспечивает последовательный выход одного агрегата. Consumer проверяет expected version. CDC даёт порядок исходного лога, однако дальнейшие партиционирование и параллелизм также должны его сохранять. Ошибка — добавить `ORDER BY id` и объявить вопрос решённым для конкурентных транзакций. Дальше — [outbox](../01-building-blocks/distributed-transactions.md#transactional-outbox).

### 29. Почему компенсация саги не равна rollback и что делать, если она падает?

Rollback отменяет незавершённые изменения внутри транзакции по протоколу СУБД. Компенсация — новая бизнес-транзакция после уже состоявшегося эффекта. Между ними другие участники могли увидеть и использовать результат; некоторые действия необратимы.

Пример: деньги списаны, товара нет. Refund возвращает деньги, но клиент уже видел списание, комиссия могла не вернуться, письмо не «разотправить». Если refund API отвечает timeout, нельзя сразу считать компенсацию неуспешной и создать новый возврат с новым ключом. Нужны стабильный compensation ID, запрос состояния, durable-журнал попыток и повтор с тем же ключом. Некоторые исходы требуют ручного разбора со связанными идентификаторами платежа и заказа.

Сага должна описывать terminal states, разрешённые переходы, deadlines и действия при поздних ответах. Резерв `PENDING` может запретить конфликтующие изменения, но это бизнес-ограничение, а не сквозная SQL-isolation. Удаление оркестратора не освобождает автоматически все резервы: нужен recovery/expiration-протокол. Ошибка — нарисовать единственную стрелку «undo» и обещать автоматическую сходимость при любых внешних отказах. Необратимые шаги по возможности ставят после точки подтверждения процесса.

### 30. Когда 2PC предпочтительнее саги и почему он не гарантирует Serializable?

2PC полезен, когда участники поддерживают prepare/commit и требуется единый исход транзакции, а цена синхронной координации приемлема. Сага подходит, когда бизнес разрешает видимые промежуточные состояния и есть корректные компенсации. Они не взаимозаменяемы по удобству реализации.

Например, перенос средств между двумя ledger-partitions в одной distributed SQL можно выполнить распределённой транзакцией. Заказ с внешним перевозчиком и платёжным провайдером обычно не имеет общей prepare-фазы: HTTP API этих сервисов не стали XA-ресурсами. Сага должна явно представить резервы, подтверждения и компенсации; она не обеспечивает мгновенный общий rollback.

2PC отвечает на вопрос «commit или abort у всех?», а изоляция отвечает на вопрос «какие конкурентные истории допустимы?». Даже при едином решении один участник может уже применить commit, пока другой ещё получает его. Глобально корректное чтение обеспечивается дополнительным протоколом СУБД. Подготовленный участник не вправе самостоятельно откатиться только из-за timeout, если могло быть принято commit-решение: нужна безопасная recovery-процедура. Ошибка — назвать 2PC «бесполезным в high-load» либо автоматическим источником полной ACID-семантики. См. [двухфазная фиксация](../01-building-blocks/distributed-transactions.md#2pc--xa-и-почему-его-не-используют-между-сервисами).

### 31. Как изменить схему таблицы без одновременного деплоя всех сервисов?

Используйте expand–migrate–contract: сначала добавьте совместимую структуру, затем переведите записи и чтения, проверьте заполнение, и только после удаления старых пользователей контракта уберите прежние поля. В rolling deployment одновременно работают минимум две версии приложения, а фоновые задачи могут отставать ещё дольше.

Например, `full_name` заменяется на `given_name`/`family_name`. Сначала добавляются nullable-поля. Новая версия умеет читать старое состояние и записывать согласованные представления в одной транзакции, если преобразование определено. Backfill идёт небольшими возобновляемыми batch с проверкой версии, чтобы старый snapshot не затёр свежее изменение. Затем чтение переключается на новые поля; старые writers должны быть остановлены или совместимо обновлены до удаления колонки.

Особый вопрос — обратимость преобразования: разбить произвольное полное имя однозначно невозможно, поэтому техническая миграция не должна придумывать бизнес-правила. DDL может требовать lock; `CREATE INDEX CONCURRENTLY` уменьшает блокирование, но имеет ограничения, дополнительную работу и возможный invalid index после ошибки. Ошибка — считать «ADD COLUMN быстро» гарантией отсутствия lock wait, а deploy rollback безопасным после destructive contract.

### 32. Как менять схему события, если старые сообщения будут replay через полгода?

Совместимость проверяется не только между сегодняшними producer и consumer, но и между новым consumer и всей поддерживаемой историей. Retention, архив, DLQ и отложенные retries определяют реальные сроки жизни старого контракта.

Например, `amount` раньше означало целое число копеек, а новая версия хочет дробное число рублей. Переиспользовать имя с новым смыслом опасно: сообщение успешно десериализуется, но сумма изменится в сто раз. Добавьте явные поля `amount_minor` и `currency` или новый тип/версию события; consumer обрабатывает обе версии с однозначным преобразованием. Новое необязательное поле обычно проще добавить, но требование default/nullable и совместимость зависят от формата и настроек schema registry.

После развёртывания новых consumers producer начинает выпускать новую форму. Старые readers нельзя отключать, пока остаётся поддерживаемый replay старых данных; возможны upcasters или отдельный migration-поток. Прогон на исторической выборке проверяет семантику, а не только схему. Для replay внешних эффектов нужен отдельный режим: повтор построения проекции не должен снова отправить клиентам письма или платежи. Ошибка — удалить старый обработчик после «все поды обновились» и забыть DLQ/архив. Связанный контекст — [потоки событий](../01-building-blocks/message-queues.md#очередь-задач-vs-поток-событий-принципиальная-разница).

### 37. Клиент загрузил 1 000 изменений одним пакетом. Что повторить, если ответ потерялся?

Сначала выберите единицу успеха. Если пакет представляет одно бизнес-действие, например замену всего прайс-листа, загрузите и проверьте новую версию отдельно, затем атомарно переключите активную версию. Пока проверка идёт, читатель должен видеть целиком предыдущий прайс. По идентификатору загрузки клиент сможет узнать исход после обрыва связи.

Если передаются независимые изменения остатков, сервис может вернуть результат каждой записи. Дайте каждой операции устойчивый идентификатор. Если эффект — изменение остатка в БД, зафиксируйте изменение и запись о выполненном идентификаторе одной транзакцией с ограничением уникальности. Иначе падение после прибавления, но до отметки о результате приведёт к повторному прибавлению. Повторяйте только элементы с неизвестным или временным исходом. Для команды «прибавить 3» простой повтор опасен. Разбейте тест на три элемента: один принят, второй отклонён по данным, при обработке третьего потерялась связь. Повтор того же пакета должен оставить первый эффект ровно один раз и позволить выяснить исход третьего. Размер сетевой пачки сам по себе не определяет границу транзакции.

### 38. Поддержка хочет единый экран по заказу, платежу и доставке. Как избежать трёх вызовов на каждое открытие?

При редких чтениях достаточно собрать ответ из трёх сервисов, ограничив время ожидания каждого и явно показывая недоступный статус. Если экран открывают 2 000 раз/с, это уже до 6 000 вызовов/с без повторов. Если изменения происходят всего 100 раз/с, рассмотрите отдельную модель чтения: сохраняйте в одной строке последнее известное состояние заказа, платежа и доставки и обновляйте её по изменениям источников.

Определите порядок отдельно для каждого владельца данных. Платёж версии 8 и доставка версии 3 принадлежат разным последовательностям: сравнение этих чисел не говорит, какая запись экрана новее. Храните версию каждого компонента, показывайте неполные данные явно и предусмотрите пересборку. При проверке доставьте старую версию платежа после новой и удалите строку модели, затем восстановите её из доступной истории или снимков. Для решения о возврате денег проверяйте допустимость операции в сервисе платежей: экран поддержки может отставать.

## На подумать

### Кейс A. «Ноль потерь» после failover

Primary подтвердил запись после remote flush на standby A. Standby B отстаёт на минуту. Primary и A одновременно недоступны; доступна только B. Бизнес требует нулевой потери подтверждённых записей и немедленного продолжения записи. Какие обещания совместимы?

<details>
<summary>Разбор</summary>

При данной конфигурации оба требования одновременно выполнить нельзя. У B нет подтверждённого клиенту хвоста, а доступ к A/primary отсутствует. Promote B с продолжением записи нарушает нулевой RPO; ожидание восстановления нужной копии нарушает требование немедленной записи. Нельзя доказать сохранность по факту «реплика синхронная когда-то была».

Нужно уточнить модель отказов и размещение копий: сколько независимых failure domains должна переживать система и какие ACK нужны до ответа клиенту. Решение может изменить топологию, quorum policy, RPO или availability-контракт, но не восстановить отсутствующие байты из арифметики. Опасный ответ — «выберем самую свежую из живых, значит не потеряем». Самая свежая доступная копия не обязательно содержит все подтверждённые операции.

</details>

### Кейс B. Дубликаты исчезли, статусы всё равно неверны

Consumer атомарно записывает inbox и меняет заказ. Из Kafka приходят `Paid(version=3)` и `Created(version=2)` с разными `event_id`. Создание запоздало, итоговый статус стал `NEW`. Что не защитил inbox?

<details>
<summary>Разбор</summary>

Inbox отсёк повтор одной идентичности события, но оба входа были уникальны. Он не гарантирует порядок и допустимость state transition. Для snapshot-событий можно применять только версию новее текущей. Для команд/дельт нужно проверять ожидаемое состояние и последовательность, а пропуски версий восстанавливать, не отбрасывать слепо.

Проверьте источник версий и причину перестановки: несколько relay, retry-topics, смена партиционирования или параллельная обработка. Простой `MAX(version)` не всегда годится: если события несут разные необходимые дельты, пропуск старой версии потеряет эффект. Опасный ответ — «увеличим TTL дедупликации»: срок хранения не решает семантику двух разных событий.

</details>

### Кейс C. Старый платёж при новом владельце задачи

Воркер A отправил `charge` внешнему провайдеру и потерял соединение. Lease истёк, воркер B получил задачу; затем A ожил. Провайдер не участвует в вашей SQL-транзакции. Как не списать деньги дважды?

<details>
<summary>Разбор</summary>

Право исполнения и платёжная идентичность различаются. A и B должны использовать один стабильный business operation ID как idempotency key провайдера; состояние `UNKNOWN` проверяется через API статуса и reconciliation. Локальный fencing не отменяет уже принятый внешним сервисом запрос. Если провайдер не поддерживает ни идемпотентность, ни надёжный lookup, строго обещать один эффект для этого окна нельзя: нужен другой протокол/провайдер или явно принятый риск с ручным разбором.

Держать SQL-lock во время HTTP не решает потерянный ответ. Генерировать новый ключ при takeover ещё опаснее: для банка это новый платёж. Срок гарантированной дедупликации провайдера должен покрывать ваши допустимые повторы; после его окончания повтор требует отдельного решения, а не автоматического retry.

</details>

В примерах используются PostgreSQL 17, классические группы потребителей и транзакции Kafka 4.1. Гарантии зависят от конфигурации.
